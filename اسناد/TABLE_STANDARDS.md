# استاندارد جداول Filament 5 (hamarehCRM)

**نسخه:** 1.0.1  
**آخرین به‌روزرسانی:** 2026-11-14  
**استک مبنا:** Laravel 13 + Filament 5 + Livewire 4 + RTL

هدف: یکدست‌سازی همه صفحات فهرست و ارائه تجربه قابل استفاده در دسکتاپ و موبایل. این سند مکمل `اسناد/PAGE_DESIGN_STANDARDS.md` و `اسناد/AGENT_RULES.md` است.

## ۱. رفتار و ناوبری رکورد

1. مقدار `recordUrl` باید آگاهانه انتخاب شود؛ برای Resourceهایی که کلیک روی ردیف نباید ویرایش ناخواسته ایجاد کند، از `recordUrl(null)` استفاده شود.
2. در صورت نیاز، `recordAction(null)` نیز تنظیم شود تا رفتار کلیک ردیف با لینک و اکشن صریح تداخل نداشته باشد.
3. ورود به ویرایش فقط از لینک نام یا اکشن مشخص و مجاز انجام شود.
4. اکشن‌های حساس فقط با مجوز واقعی نمایش داده شوند؛ مخفی بودن دکمه جایگزین Policy نیست.
5. اکشن مخرب و Bulk حساس باید تأیید روشن و متن نتیجه فارسی داشته باشند.

## ۲. ستون‌ها و داده

6. وضعیت‌هایی مانند `is_active` با Badge یا Icon معنادار نمایش داده شوند؛ تغییر وضعیت باید تأیید/بازخورد مناسب داشته باشد.
7. نوع و محدوده مدل در ستون مستقل و قابل فهم نمایش داده شود.
8. اعداد و مبلغ‌ها فقط با `App\Support\Fa` قالب‌بندی شوند.
9. تاریخ و زمان با ابزار استاندارد پروژه و تقویم شمسی مورد توافق نمایش داده شوند.
10. ستون‌های کم‌کاربرد به‌صورت پیش‌فرض پنهان و در صورت پشتیبانی API نسخه نصب‌شده، قابل انتخاب باشند.
11. `defaultSort` باید صریح و پایدار باشد.
12. pagination با گزینه‌های `[10, 15, 25, 50, 100]` و کلیدهای انگلیسی انجام شود؛ کلید فارسی برای پارامتر pagination ممنوع است.

## ۳. فیلتر، حالت خالی و حذف نرم

13. فیلترها به‌صورت پیش‌فرض در ناحیه dropdown استاندارد Filament باشند؛ از نوار سنگین AboveContent بدون نیاز روشن پرهیز شود.
14. Empty State باید عنوان، توضیح کوتاه و در صورت داشتن مجوز، اکشن ایجاد داشته باشد.
15. برای مدل‌های Soft Delete، فیلتر رکوردهای حذف‌شده و اکشن‌های Restore/ForceDelete مطابق مجوز و سیاست نگهداری داده ارائه شوند.
16. عملیات گروهی باید محدود، قابل فهم و همراه با تأیید متناسب با ریسک باشد.

## ۴. واکنش‌گرایی و موبایل

17. جدول نباید در موبایل صرفاً با کوچک‌کردن فونت به تجربه قابل قبول تبدیل شود.
18. برای هر جدول، یکی از الگوهای زیر آگاهانه انتخاب و در تست موبایل تأیید شود:
   - جدول واکنش‌گرا با ستون‌های ضروری و اسکرول کنترل‌شده؛
   - نمایش فشرده/stacked در صورت پشتیبانی واقعی Filament 5؛
   - کارت موبایل اختصاصی برای رکوردها، در حالی که همان Query، مجوزها، فیلترها و داده مرجع جدول را مصرف می‌کند.
19. کارت موبایل باید اطلاعات ضروری و اکشن‌های پرتکرار را نشان دهد؛ از نمایش دوباره یا ناسازگار داده با جدول جلوگیری شود.
20. اکشن‌های اصلی باید در محدوده دسترس انگشت باشند و دکمه‌های مخرب از اکشن اصلی تفکیک شوند.
21. تصمیم نمایش دسکتاپ/موبایل برای هر Resource باید مستند و در عرض‌های واقعی موبایل و تبلت آزمایش شود.

## ۵. چندشرکتی و امنیت

22. Query جدول باید در محدوده شرکت جاری باشد؛ هیچ جدول، فیلتر، شمارنده یا Bulk Action نباید داده شرکت دیگر را افشا کند.
23. فیلترهای انتخاب رابطه نیز باید به شرکت جاری محدود شوند.
24. Policy و مجوز در سطح Query و Action رعایت شوند؛ پنهان‌کردن ستون یا دکمه کنترل امنیتی محسوب نمی‌شود.
25. تست دسترسی حداقل شامل دو شرکت و کاربرانی با نقش‌های متفاوت باشد.

## ۶. چک‌لیست پذیرش Resource جدید

- [ ] رفتار `recordUrl` و `recordAction` مشخص است.
- [ ] لینک نام و اکشن‌های ردیف روشن و مجازند.
- [ ] ستون وضعیت و نوع داده قابل فهم است.
- [ ] قالب اعداد و تاریخ از ابزارهای مشترک استفاده می‌کند.
- [ ] فیلترها در جایگاه استاندارد هستند.
- [ ] Empty State و اکشن ایجاد مجاز وجود دارد.
- [ ] pagination و defaultSort صریح هستند.
- [ ] Soft Delete و Bulk Action مطابق مجوز پیاده شده‌اند.
- [ ] داده‌ها به شرکت جاری محدود هستند.
- [ ] نمایش موبایل به‌صورت واقعی آزمایش شده است.
- [ ] CSS از Design System مشترک استفاده می‌کند.

## ۷. سازگاری API

این سند رفتار و معیار پذیرش را تعیین می‌کند، نه اینکه وجود یک متد خاص را در همه نسخه‌ها تضمین کند. پیش از استفاده از هر متد یا کلاس Filament، API باید با Filament 5 نصب‌شده در پروژه و مستندات همان نسخه تطبیق داده شود. از کپی‌کردن مثال‌های Filament 4 یا نسخه‌های قدیمی بدون بررسی خودداری شود.
